# Changelog

A changelog contains a curated, chronologically ordered list of notable changes for each version of a project. This file contains the changelog. All notable changes to this project will be documented in this file.

<!-- #region blockquote -->

<blockquote>

**Tags:**

<!-- #region ⚙️ [Types of changes] -->

<details>
<summary>⚙️ [Types of changes]</summary>

> - Added for new features.
> - Changed for changes in existing functionality.
> - Deprecated for soon-to-be removed features.
> - Removed for now removed features.
> - Fixed for any bug fixes.
> - Security in case of vulnerabilities.

</details>

<!-- #endregion  [Types of changes] -->

<!-- #region 💥 [Breaking Change] -->

<details>
<summary>💥 [Breaking Change]</summary>

> A breaking change in a changelog is an update to software that breaks existing user code, integrations, or workflows when upgrading to a new version. It requires developers or users to manually modify their own code or settings to make things work again.

</details>

<!-- #endregion 💥 [Breaking Change] -->

<!-- #region 🚀 [New Feature] -->

<details>
<summary> 🚀 [New Feature]</summary>

> A changelog new feature entry is a specific update in a project's chronological log that announces newly added capabilities, tools, or content. It lets users and developers know what functionality is now available that did not exist in previous versions.

</details>

<!-- #endregion 🚀 [New Feature] -->

<!-- #region 🐛 [Bug Fix] -->

<details>
<summary>🐛 [Bug Fix]</summary>

> A changelog bug fix is a written record or entry in a software update list that explains an error, glitch, or broken feature that has been successfully repaired.

</details>

<!-- #endregion 🐛 [Bug Fix] -->

<!-- #region 📝 [Documentation] -->

<details>
<summary>📝 [Documentation]</summary>

> A changelog documentation is a curated, chronological log of notable updates, enhancements, bug fixes, and changes made to a project or software over time. It usually lists versions from newest to oldest to help users and developers track product evolution.

</details>

<!-- #endregion 📝 [Documentation] -->

<!-- #region 🏠 [Internal] -->

<details>
<summary>🏠 [Internal]</summary>

> An internal changelog is a private, technical record maintained by a development or product team. It tracks every modification made to a software project—including backend code refactors, dependency updates, and bug fixes—providing a clear audit trail for engineers and internal staff.

</details>

<!-- #endregion 🏠 [Internal] -->

<!-- #region 💅 [Polish] -->

<details>
<summary>💅 [Polish]</summary>

> A changelog Polish refers to a small round of general improvements, bug fixes, user interface refinements, and design clean-ups listed in a product's update log. Alternatively, it can mean adding support for the Polish language to a software's interface.

</details>

<!-- #endregion 💅 [Polish] -->

<!-- #region 🏃‍♀️ [Performance] -->

<details>
<summary>🏃‍♀️ [Performance]</summary>

> A changelog performance entry is a specific update note documenting speed enhancements, resource optimization, and efficiency gains made in a software version. It highlights how code changes reduce load times, lower memory usage, or improve response speed for users.

</details>

<!-- #endregion 🏃‍♀️ [Performance] -->

<!-- #region 🔬 [Output Optimization] -->

<details>
<summary>🔬 [Output Optimization]</summary>

> Changelog output optimization refers to the process of making software update logs cleaner, smaller, and easier for both humans and AI tools to read. It reduces file sizes, removes messy developer code text, and formats records neatly.

</details>

<!-- #endregion 🔬 [Output Optimization] -->

<!-- #region 👓 [Spec Compliance] -->

<details>
<summary>👓 [Spec Compliance]</summary>

> Changelog spec compliance means that a project's list of changes follows a strict, formal set of rules or standard formats (such as [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)). This compliance ensures that version numbers, dates, and change categories like added features or bug fixes are organized in a predictable way for both people and automated tools.

</details>

<!-- #endregion 👓 [Spec Compliance] -->

<br>
_Note: Gaps between patch versions are faulty, broken or test releases._

</blockquote>
